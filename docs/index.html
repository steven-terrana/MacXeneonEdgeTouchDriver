Focus restore: from broken ritual to verified fast path

After every gesture the driver returns focus to the window that had it before the touch. The baseline ran an eight-call accessibility sequence plus a synthetic title-bar click on every tap — and its own verification said it almost never worked. The verification itself was the bug: CFEqual fails across separately copied AXUIElement tokens. With a pid-based comparison and a staged escalation ladder, 90% of restores now complete with a single read-only check, and all of them verify — including genuine cross-application restores introduced by the inactive-window fix.

Drag responsiveness under load

Deterministic benchmark: 500 drag moves burst into the pipeline while the consumer takes 2 ms per event, simulating a busy system. The baseline queued and replayed every stale position — the cursor lagged over a second behind the finger. Move coalescing keeps only the newest position, so staleness stays bounded and the cursor lands exactly where the finger is.

New capability: first touch on inactive windows

macOS consumes a click in an inactive window to activate it, so the baseline driver's first tap on an unfocused kiosk did nothing visible — and because the driver restores focus after every gesture, every tap became activation-only. The driver now resolves the window under the touch point and activates it before the mouse-down. The cost profile below shows the fix is nearly free when the target is already focused, which is the common case.

Methodology

Live captures tail the driver's structured metric log for ~90 seconds while the touchscreen is exercised with a fixed protocol: repeated taps and drags on the Xeneon display, alternating between a lightweight focused app and a heavy one, and (final capture) between kiosk-focused and primary-display-focused so cross-application paths are exercised. All timings are measured inside the driver from HID report arrival timestamps to synthetic event posting; percentiles are computed over each capture. Same physical hardware, same machine state discipline (driver restarted, binary verified against the build) for every capture.

Deterministic benchmarks drive the production application object with fake input sinks and cursor controllers, so results measure driver code, not CoreGraphics. Scenarios: 10,000-move drag burst (throughput), 500-move backlog with a 2 ms/event consumer (staleness), and 1M-report parser throughput (regression guard — unchanged at ~26 ns/report throughout). Three runs per phase; representative run shown.

Honest accounting: the final capture's hid-to-down and tap-complete p99 values (49.1 / 16.6 ms) are inflated relative to p50 by design — they include the ~5 cross-application taps where the driver waits up to 50 ms for the target window to activate before posting the mouse-down. The baseline had no such wait because it could not perform this action at all. Sample sizes are modest (34–58 taps per capture); medians are stable across captures, tails are indicative.
